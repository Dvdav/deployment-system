# DS-002 — Nexus 3 Connections — Technical Specification (RU)

**Проект:** Deployment System  
**Статус:** Согласованные требования для реализации; реализация и приёмка не завершены  
**Дата:** 25 ноября 2026  
**Предшествующий этап:** DS-001 Foundation (не изменять в рамках DS-002)  
**Следующий этап:** DS-003 Maven Artifact Sources / Artifacts

## 1. Цель и границы

Управление несколькими подключениями к Nexus Repository Manager 3 и зарегистрированными в DS репозиториями: безопасное хранение credentials, обязательные проверки, управление жизненным циклом, UI и общий контракт проверки внешних интеграций.

DS-002 включает регистрацию репозиториев с ручной классификацией SNAPSHOT/RELEASE, но не ограничивается Maven. Поиск/выбор артефактов, привязка источников к компонентам, promotion, автоматический импорт репозиториев, polling и реализация Jenkins/Ansible/Deployment Planning не входят в DS-002. Последующие модули используют его сервисные границы.

## 2. Подключения: функциональные правила

- Четыре логических поля: name (обязательно), URL (обязательно, HTTPS), token credentials (обязательно), description (необязательно). Только токенные credentials через HTTP Basic в фактически поддерживаемом Nexus формате; не предполагать Bearer или обычный парольный режим. Если нужны token username и passcode, безопасно поддержать обе части.
- Несколько ACTIVE подключений. Имя уникально среди ACTIVE без учёта регистра, исходное написание сохраняется. Нормализованный URL уникален среди ACTIVE: убрать завершающий слеш и стандартный HTTPS-порт 443, lowercase host, сохранить путь.
- URL неизменяем после создания даже без зависимостей. Для другого URL создать новое подключение. Name/description и замена credentials разрешены при наличии зависимостей; UUID сохраняется.
- Создание и замена credentials: один Save, обязательный backend Check именно сохраняемых URL/credentials; клиентский флаг или ранее выполненная проверка не заменяют Check. Сохранение только при успехе, со статусом VERIFIED. При ошибке новая запись не создаётся, старые credentials и состояние сохранённого подключения не меняются.
- Старые credentials никогда не возвращаются через API или UI. Замена — явное действие Replace Token с новым шифрованием.
- Delete означает ACTIVE → INACTIVE, без физического удаления. Обычные списки и выбор для нового использования исключают INACTIVE. Исторические ссылки и snapshots сохраняются. Активные зависимости блокируют деактивацию, backend возвращает их список.
- Повторное использование имени/URL после деактивации допускается с новым UUID. Restore/Reactivation подключения в MVP нет; административное восстановление не специфицировано.
- Optimistic Locking: техническое поле version, ожидаемая версия клиента и атомарное сравнение/увеличение при изменении конфигурации. При несовпадении HTTP 409 Conflict. Не держать транзакцию БД во время внешней проверки; после неё условно сохранить с проверкой version.

## 3. Зарегистрированные репозитории

- У сохранённого NexusConnection имеется отдельный список всех ACTIVE репозиториев, зарегистрированных в DS, а не полный список внешнего Nexus.
- Add Repository: оператор вводит имя и выбирает ровно один тип SNAPSHOT или RELEASE. Гибридный тип запрещён. Не импортировать дополнительные метаданные формата/типа и не ограничивать регистрацию Maven.
- Backend проверяет существование и доступность репозитория на соответствующем Nexus с credentials подключения. Только после успеха сохраняет или восстанавливает запись; при ошибке безопасная диагностика, без изменения списка. Не пересохранять настройки подключения.
- Имя и тип неизменяемы. Удаление означает логическое архивирование в DS, не удаление на внешнем Nexus. Активные зависимости (например использование в активном релизе или профиле) блокируют архивацию с диагностикой; исторические ссылки сохраняются. Архивные записи исключены из обычных списков и нового использования.
- Повторное добавление при совпадении UUID NexusConnection, имени и типа восстанавливает архивную запись с прежним UUID после успешной проверки. Если тип другой, создаётся новая запись с новым UUID, прежняя остаётся архивной. При неуспешной проверке ничего не восстанавливать и не создавать.
- Для одного NexusConnection и имени максимум одна ACTIVE запись независимо от типа. Backend и PostgreSQL обеспечивают запрет, в том числе при конкурентных запросах. Для смены типа сначала архивировать старую запись, затем зарегистрировать нужный тип по указанным правилам.

## 4. Общий контракт проверки интеграций

Общий Java-интерфейс с независимыми реализациями (Strategy), отделёнными от моделей хранения:
- checkConnection принимает конфигурацию проверяемого подключения (включая ещё не сохранённые credentials), проверяет доступность сервера и авторизацию, без конкретного ресурса.
- checkResource дополнительно принимает идентификатор/имя ресурса и проверяет его существование и доступность.
- DS-002 реализует интерфейс, CheckResult и NexusCheckService. JenkinsCheckService и AnsibleCheckService добавляются в соответствующих будущих этапах для Pipeline и Job Template. Не создавать отдельный микросервис.
- Save, регистрация/восстановление репозитория, самостоятельная проверка и будущая предпроверка deployment используют этот же контракт.

CheckResult: status, errorCode, безопасное message, checkedAt.

| status | Цвет | Значение |
|---|---|---|
| SUCCESS | Зелёный | Проверка успешна |
| DEGRADED | Жёлтый | Сервер отвечает, но есть проблемы (авторизация, права, API), либо проверка невозможна по локальной причине, например недоступный ключ |
| UNREACHABLE | Красный | Сервер недоступен, сетевая ошибка или таймаут подключения |

Не считать локальную ошибку доказательством недоступности сервера. UI показывает причину и время проверки при наведении. Это результат последней проверки, не непрерывный мониторинг.

Проверка Nexus 3: реальный защищённый API с HTTP Basic token credentials, HTTPS, connect/read timeouts. Предпочтительно запрос информации о текущем аутентифицированном пользователе, если целевая версия и права позволяют; публичный/анонимный health endpoint не доказывает валидность токена. Фактический endpoint, минимальные права и формат credentials подтвердить на реальном Nexus; при отсутствии подходящего endpoint согласовать альтернативу с теми же гарантиями.

Хранить verificationStatus (NOT_VERIFIED / VERIFIED / CHECK_FAILED), lastCheckedAt и безопасный lastCheckErrorCode. VERIFIED соответствует успеху, CHECK_FAILED — неуспешной выполненной проверке; метаданные позволяют различать DEGRADED/UNREACHABLE. NOT_VERIFIED до первой проверки остаётся техническим открытым вопросом UI; не выдавать отсутствие проверки за успешную. Результат проверки новых несохранённых credentials не заменяет результат проверки прежних. Обновлять состояние по фактическим проверкам сохранённого подключения, включая будущую предпроверку deployment. Ошибка конкретного ресурса не является доказательством сетевой недоступности сервера. Без polling и отдельного аудита Check.

## 5. Шифрование и секреты

Общий переиспользуемый Java Encryption Service внутри модульного монолита, не привязанный к Nexus. AES-256-GCM, новый криптографически случайный 96-битный nonce при каждом шифровании, ciphertext, authentication tag (в payload или отдельно), nonce, keyId. Nonce — отдельный параметр AES-GCM, не часть исходного токена. Расшифровка по keyId; неверный tag/ключ приводит к безопасной ошибке.

Ключи вне БД и Git, загружаются в память из защищённого внешнего YAML: active-key-id и map keyId → Base64 32-byte key. Base64 не шифрование. Доступ к файлу только технической учётной записи и уполномоченным администраторам. Vault отложен. Нет отдельной таблицы ключей.

Отсутствие/некорректность активного ключа не блокирует запуск приложения: блокируются операции нового шифрования; существующие доступные credentials остаются пригодными. Отсутствие исторического ключа или повреждённые credentials блокируют только операции с соответствующим секретом. Не раскрывать токены, plaintext, ключи, ciphertext в административном аудите, Authorization headers в API, логах, UI, snapshots или диагностике. Production credentials не передавать по HTTP.

### Ручная ротация

- Административная CLI-команда того же Java-приложения, отдельный режим запуска без обычного сервиса; без REST, UI и фоновой автоматизации.
- Остановить все экземпляры, способные менять credentials; исключить параллельные команды ротации.
- Добавить новый ключ во внешний YAML, назначить активным, сохранить старые ключи.
- Каждая запись в отдельной транзакции: пропустить записи с активным keyId, остальные расшифровать старым ключом и перешифровать активным со свежим nonce. Ciphertext/nonce/tag/keyId обновлять атомарно.
- Повторный запуск после прерывания безопасно продолжает оставшиеся записи. Старые ключи не удалять до проверки всех записей, включая INACTIVE, и учёта резервных копий.

### Правила для будущих этапов

Общее правило для Nexus, Jenkins и Ansible: недоступность credentials целевого окружения не блокирует создание/редактирование Release при выполнении обычных требований. Недоступный Nexus блокирует поиск/выбор новых версий через него. Deployment Planning проверяет все необходимые конкретному deployment credentials и блокирует запуск при невозможности расшифровки хотя бы одного; безопасная диагностика указывает затронутое подключение/окружение. Не менять статус Release; независимые окружения и подключения работают при выполнении своих гейтов. Реализация этих интеграций в последующих этапах.

## 6. Модель данных (PostgreSQL / Flyway)

### nexus_connection

- id UUID PK, неизменяемый;
- name, url, description (nullable);
- encryptedCredentials, keyId, nonce, authenticationTag (отдельно или в payload);
- status ACTIVE/INACTIVE;
- verificationStatus NOT_VERIFIED/VERIFIED/CHECK_FAILED;
- lastCheckedAt, lastCheckErrorCode (nullable);
- version для Optimistic Locking;
- createdAt, updatedAt, deactivatedAt (nullable для активной записи).

Partial unique indexes для ACTIVE по имени без учёта регистра и нормализованному URL. Обязательность полей и ограничения статусов обеспечиваются БД.

### nexus_repository

- id UUID PK;
- nexus_connection_id UUID FK на nexus_connection;
- name;
- type SNAPSHOT/RELEASE;
- status ACTIVE/INACTIVE;
- created_at, updated_at, archived_at.

Credentials только на уровне nexus_connection. Partial unique index по (nexus_connection_id, name) для ACTIVE, без type. Архивирование и восстановление сохраняют идентичность по правилам раздела 3.

## 7. REST и dependency guards

Две группы REST API: nexus-connections и nexus-connections/{id}/repositories. Самостоятельный endpoint проверки сохранённого подключения не изменяет его конфигурацию и не заменяет обязательную проверку при Save. Конкретные маршруты, DTO и error contract — детали реализации, кроме согласованного HTTP 409 для устаревшей version.

Перед деактивацией подключения или архивацией репозитория backend вызывает общий расширяемый механизм проверки активных зависимостей. DS-002 реализует механизм для обеих операций; конкретные проверки компонентов, профилей и активных релизов подключаются по мере появления соответствующих модулей. Не создавать фиктивные таблицы/FK к отсутствующим модулям. При блокировке возвращать безопасную диагностику и список зависимостей; исторические ссылки сохранять. Техническая атомарность проверки/архивации определяется при реализации; последующие модули исключают гонку создания зависимости с архивацией.

## 8. Frontend React UI

- Master-detail: слева список ACTIVE Nexus по имени и один цветовой кружок; справа форма выбранного подключения. Одновременно редактируется одно подключение, без вкладок.
- При смене подключения с несохранёнными изменениями показать подтверждение; при отказе остаться, при согласии сбросить изменения и открыть выбранное.
- Name/description редактируемы, URL read-only после создания; сохранённый токен не отображается. Replace Token открывает ввод нового токена.
- Один Save для создания/замены credentials; отдельная кнопка Check не нужна. Показывать прогресс, блокировать повторные клики; ошибка не уничтожает сохранённые данные.
- Цвет, причина и время проверки по разделу 4. При HTTP 409 показать конфликт и предложить обновить данные, без автоматической перезаписи.
- Под четырьмя полями выбранного Nexus показывать список/таблицу всех его активных зарегистрированных репозиториев. Add Repository открывает имя и выбор SNAPSHOT/RELEASE; отдельный Save. При успехе строка сразу появляется, при ошибке список не меняется.
- Имя/тип репозитория не редактируются. Архивирование, восстановление через повторный Add и ошибки дубликатов отражаются в списке. При зависимостях показать отказ и список зависимостей от backend. Отдельный экран архива не согласован.

## 9. Аудит

Аудировать административные изменения конфигурации подключения (создание, разрешённые поля, замена credentials, деактивация): actor, timestamp, ID, операция и несекретные изменённые поля. Не записывать token, ciphertext, Authorization или ключи. Проверки соединения не создают отдельного audit event. Детальный аудит операций репозиториев не специфицирован отдельно.

Definition of Done:
- [ ] Миграции, FK, статусы, обязательные поля и ограничения уникальности проверены, включая конкурентные вставки.
- [ ] CRUD подключений, неизменяемый URL, независимость подключений, обязательная проверка перед Save, отсутствие сохранения при ошибке, сохранение старых credentials/статуса при неудачной замене.
- [ ] Архивация подключения и репозитория сохраняет историю, исключает новое использование; механизм зависимостей блокирует обе операции и возвращает список (в DS-002 тестовая реализация/моки).
- [ ] Регистрация, восстановление прежнего UUID при совпадении, новый UUID при другом типе, отказ при двойной ACTIVE регистрации, отказ при неуспешной проверке.
- [ ] Optimistic Locking, конфликт 409, в том числе изменение во время Check без открытой транзакции; UI не перезаписывает чужие изменения.
- [ ] Общий интерфейс и CheckResult; отдельные проверки подключения и ресурса; самостоятельная проверка без изменения конфигурации; успешный аутентифицированный ответ, сетевые ошибки, timeout, неверные credentials, права, API и локальные ошибки; публичный endpoint не доказывает авторизацию.
- [ ] UI master-detail, предупреждение о несохранённых изменениях, валидация, скрытие credentials, Save/progress, три согласованных цвета, причина/время, управление репозиториями и зависимости.
- [ ] AES-GCM round-trip, свежие nonce, неверный/отсутствующий ключ и повреждённые данные/tag; загрузка YAML; изоляция ошибок, совместная доступность ключей, новые записи с активным ключом; CLI rotation/recovery с атомарностью на запись, пропуском уже обработанных и возобновлением после прерывания.
- [ ] Нет утечек секретов в API/логах/UI/audit/snapshots; административный аудит без отдельных Check events.
- [ ] Автоматизированные тесты успешны, ручные проверки на реальном Nexus 3 выполнены и задокументированы, оператор подтвердил приёмку.

Реальные проверки зависимостей других модулей, Jenkins/Ansible и предпроверка deployment тестируются в последующих этапах, а не считаются выполненными в DS-002.

## 11. Открытые технические уточнения

- Фактический формат Nexus HTTP Basic token credentials, защищённый endpoint и минимальные права; API проверки репозитория, подтвердить на реальном Nexus. Допустимость локальных тестовых HTTP endpoint уточнить без передачи production secrets.
- Точные REST-маршруты/DTO/error contract, путь YAML, синтаксис CLI, техническая реализация dependency guards и защиты от гонок; точные будущие связи с DS-003.
- Отображение NOT_VERIFIED до первой проверки. Обычное создание и замена credentials уже требуют успешной проверки, поэтому не вводить новый цвет без согласования.
- Точные правила хранения/обновления диагностических метаданных при проверке конкретного ресурса, архивировании родительского подключения и конкурентных проверках не детализированы; не считать новые правила утверждёнными.
- Детализация аудита операций репозиториев не согласована отдельно.
