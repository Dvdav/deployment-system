# DS-002 — Nexus 3 Connections — Technical Specification (RU)

**Проект:** Deployment System  
**Статус:** Specification baseline для разбора задач; реализация не начата  
**Дата:** 24 ноября 2026  
**Предшествующий этап:** DS-001 Foundation (не изменять в рамках DS-002)  
**Следующий этап:** DS-003 Maven Artifact Sources / Artifacts

## 1. Цель и границы

Предоставить оператору интерфейс управления несколькими подключениями к Nexus Repository Manager 3: регистрация, изменение параметров, безопасное хранение токенных учётных данных, ручная проверка соединения и логическое удаление.

В DS-002 **не входят** регистрация Maven repositories / ArtifactSource, RELEASE/SNAPSHOT, поиск и выбор артефактов, promotion, массовая автоматическая загрузка репозиториев и периодический мониторинг Nexus. Это предмет следующих этапов, прежде всего DS-003.

## 2. Принятые решения

| Область | Решение |
|---|---|
| Несколько серверов | Поддерживать несколько отдельных Nexus 3 connections |
| Авторизация | Для MVP только токенные учётные данные, передаваемые через **HTTP Basic Authentication** в формате, поддерживаемом фактическим Nexus; обычный парольный режим не проектировать |
| Хранение | Токенные учётные данные в PostgreSQL **только в зашифрованном виде** |
| Криптография | AES-256-GCM; отдельный случайный 96-битный nonce для каждой операции шифрования; сохранить ciphertext, authentication tag, nonce и keyId |
| Ключи | Материал секретных ключей находится вне приложения/БД, передаётся через защищённую конфигурацию/секрет; keyId — только несекретный идентификатор |
| Ротация | **Отдельная ручная процедура**, без пользовательского UI/автоматического фонового вращения ключей |
| Проверка | Только кнопка **Check Connection**, без расписания |
| Сохранение | Можно сохранить подключение даже без успешного Check Connection |
| URL | Изменение URL **запрещено при наличии зависимостей**; показать список зависимостей |
| Аудит | Аудировать изменения конфигурации, а **не** каждую проверку соединения |
| Удаление | **Soft delete:** ACTIVE → INACTIVE; исторические записи и ссылки сохраняются |
| Деактивация | При активных зависимостях блокировать, показать список зависимостей |
| Восстановление | **Нет reactivation через UI в MVP**; оператор создаёт новую запись. Возможное административное восстановление отложено |

## 3. Функциональное поведение

### 3.1. Создание подключения

Оператор вводит:
- **Name** — обязательное уникальное читаемое имя подключения;
- **URL** — обязательный HTTPS endpoint Nexus (точные правила локальных тестовых HTTP endpoint согласовать при реализации; production-секреты по HTTP не передавать);
- **Token credentials** — обязательные токенные учётные данные Nexus в форме, необходимой для HTTP Basic; frontend не должен предполагать, что произвольная строка может использоваться как Bearer token;
- **Description** — необязательное описание.

Система разрешает несколько подключений. Создание не требует успешной проверки соединения: в отсутствие успешной проверки статус NOT_VERIFIED. При сохранении токенные данные шифруются до записи в PostgreSQL.

**Интеграционное уточнение, не новое функциональное решение:** проверить на реальном Nexus, какие именно части токенных учётных данных нужны для заголовка HTTP Basic (например, token username и token passcode). Если фактический формат требует две части, форма и секретное хранилище должны безопасно поддерживать обе; не выдумывать формат и не класть секретные части в открытые поля.

### 3.2. Просмотр и редактирование

Основной список показывает только ACTIVE connections. Поддержать просмотр имени, URL, описания, результата/времени последней проверки и действия редактирования, проверки, деактивации.

Редактирование Name/Description допускается с обычной валидацией. Токенные credentials можно **заменить**, но нельзя получить старое значение через API или UI. При замене требуется новое шифрование со свежим nonce. После изменения URL/credentials предыдущий успешный статус не должен вводить в заблуждение: результат проверки сбрасывается в NOT_VERIFIED до нового Check Connection.

Если к Nexus существуют зависимости, **запретить изменение URL**, показать связанные ArtifactSource/repositories и компоненты; проверить блокировку на backend в момент изменения, а не только в UI. До реализации DS-003 зависимостей может не быть, но интерфейс/сервисная граница должна позволять такую проверку без изменения принятого правила.

### 3.3. Check Connection

Только ручной запуск оператором через UI. Backend выполняет реальный сетевой запрос к защищённому endpoint Nexus API, требующему авторизации, с разумными connect/read timeouts и безопасной обработкой ошибок. Нельзя считать успешным Check Connection только доступность TCP/главной страницы, не проверив авторизацию.

Статусы:
- **NOT_VERIFIED** — с момента создания либо изменения credentials/URL не было успешной проверки (и/или проверки ещё не выполнялись);
- **VERIFIED** — последняя выполненная проверка успешна;
- **CHECK_FAILED** — последняя выполненная проверка завершилась ошибкой.

Хранить время последней попытки и безопасную категорию/краткую причину ошибки: недоступность/таймаут, неверная авторизация, прочая ошибка. VERIFIED — **результат последней проверки**, а не обещание постоянной доступности. Не делать background polling и не писать Check Connection в административный аудит.

При неуспешной проверке подключение не удаляется и не блокирует сохранение. Никакой автоматической загрузки полного списка репозиториев.

### 3.4. Логическое удаление

Пользователь выбирает Delete, но физическое удаление строки не выполняется: ACTIVE → INACTIVE. INACTIVE исключён из обычного списка и из выбора для новой конфигурации/исполнения. **Исторические ReleaseManifest и DeploymentExecution сохраняют достоверные ссылки и snapshots**, включая неизменяемые идентификаторы; архивная история не зависит от видимости текущего подключения.

**Если есть активные связи с ArtifactSource или компонентами**, действие блокируется. UI отображает список этих зависимостей и объяснение; backend проверяет повторно непосредственно перед изменением статуса. Исторические связи сами по себе не запрещают перевод в INACTIVE, иначе soft delete потеряет смысл.

Для INACTIVE нет кнопки Restore/Re-activate в MVP. Для повторного использования оператор создаёт новое подключение с новым ID. Административная процедура восстановления пока не специфицирована и не входит в MVP.

## 4. Шифрование и обращение с секретами

Использовать AES-256-GCM с криптографически стойко генерируемым **новым 12-байтовым nonce при каждом шифровании**; nonce нельзя повторно использовать с тем же ключом. Хранить ciphertext и authentication tag (вместе либо раздельно), nonce и keyId. **Nonce не добавляется к исходному токену перед шифрованием**: это отдельный параметр AES-GCM. При расшифровке использовать сохранённые nonce, tag и ключ по keyId.

Настоящие секретные ключи не хранить в PostgreSQL, git, логах, API ответах, snapshots или audit. Для локального MVP допустима инъекция ключевого материала через секретную конфигурацию/переменную окружения, при условии отсутствия утечки в репозиторий/логи; корпоративный secret manager может быть добавлен позже. Если требуемого ключа нет или authentication tag не проходит проверку, операция безопасно завершается ошибкой без возврата исходных данных.

Ротация: отдельная **оператором/администратором запускаемая процедура**; добавить новый ключ, обеспечить одновременную доступность старого и нового во время ротации, перешифровывать каждую запись с новым nonce, проверять результат и обновлять keyId, затем выводить старый ключ из обращения **только после подтверждённого завершения**. Ошибки не должны приводить к утере токенов. Конкретный CLI/скрипт, транзакционная модель и recovery будут детализированы в задаче по криптографии; автоматически запускаемую периодическую ротацию не вводить.

В HTTP-логах, исключениях, мониторинге, UI и аудите не показывать токены, Basic Authorization headers, секретные ключи или их расшифрованные значения. Транспорт до Nexus в рабочей среде должен защищать Basic credentials (HTTPS).

## 5. Предварительная модель данных

`NexusConnection` (логическая модель; физическая миграция в отдельной задаче):
- `id`: UUID, неизменный;
- `name`: unique, required;
- `url`: required;
- `description`: nullable;
- `encryptedCredentials`: encrypted payload (токенные Basic credentials);
- `keyId`: identifier of encryption key;
- `nonce`: per-encryption unique 12 bytes;
- `authenticationTag`: GCM authentication tag (либо часть encrypted payload);
- `status`: ACTIVE / INACTIVE;
- `verificationStatus`: NOT_VERIFIED / VERIFIED / CHECK_FAILED;
- `lastCheckedAt`: nullable timestamp;
- `lastCheckErrorCode`: nullable safe error category;
- `createdAt`, `updatedAt`;
- `deactivatedAt`: nullable.

Сохранить IDs для будущих FK из DS-003 (ArtifactSource → NexusConnection), но **не создавать функциональность DS-003 внутри DS-002**. Правила повторного использования имени после деактивации, точный REST контракт, схема аудита и способ хранения token username/passcode фиксируются при детализации соответствующих задач без изменения принятых бизнес-решений.

## 6. Аудит

Записывать создание подключения, изменение полей/URL, замену токенных учётных данных и деактивацию: actor, timestamp, connection ID, тип операции, несекретные изменённые поля. **Не записывать исходный/новый token, ciphertext или HTTP authorization headers.** Успех/неуспех ручной проверки отражается только в текущем состоянии NexusConnection; отдельное событие audit не требуется.

## 8. Definition of Done для DS-002

- Можно независимо зарегистрировать несколько Nexus 3 connections.
- Токенные Basic credentials сохраняются в зашифрованном виде, не раскрываются через API/логи/аудит, ключевой материал отсутствует в DB.
- Ручная Check Connection действительно проверяет авторизованный доступ к Nexus, различает success/auth/network/other error и сохраняет время.
- Connection можно сохранить и без успешной проверки; автоматический мониторинг отсутствует.
- Редактирование, замена токена и запрет URL changes при зависимостях проверены.
- Soft delete оставляет строку и исторические связи, блокируется при активных зависимостях, не предлагает Restore в UI.
- Аудит включает изменения конфигурации и исключает результаты Check Connection и секреты.
- Проверены key rotation/recovery, неверный ключ/tag/nonce, таймауты, отсутствие утечки Basic Authorization.
- Backend/frontend/integration/E2E тесты проходят; предъявлены реальные результаты проверки на Nexus или честно задокументировано отсутствие доступа к тестовому Nexus.
- Приёмка выполнена оператором; до неё не объявлять реализацию завершённой.
