# DS-006 — Deployment Planning: обзор и декомпозиция
**Проект:** Deployment System · **Дата:** 19.11.2026 · **Статус:** согласованная архитектура; технические спецификации частей требуют детализации перед реализацией.

## Цель
Сформировать проверяемый и фиксируемый DeploymentPlan на основании immutable ACTIVE ReleaseManifest, размещения компонентов по EnvironmentServer, DeploymentProfile/ExecutionDefinition и ComponentDependency. DeploymentPlan описывает *что, где и в каком порядке* делать. DeploymentExecution/история фиксирует *что произошло*. Настоящий запуск Jenkins/Ansible и Temporal orchestration относятся к DS-007.

## Сквозные утверждённые ограничения
- Immutable ReleaseManifest, snapshot DeploymentPlan при запуске; версия артефакта в плане не редактируется.
- Операции: STOP, DEPLOY, START, VALIDATE; STOP/START/VALIDATE настраиваемые; VALIDATE — после последней операции, приводящей сервис в рабочее состояние.
- Между независимыми компонентами — последовательное выполнение по умолчанию с ручной перестановкой, только если ограничения зависимостей соблюдены. На необходимых серверах одного компонента — ALL_AT_ONCE.
- Dependency graph автоматически обнаруживается; никакого молчаливого STOP/START компонентов вне Release.
- DS history, а не опрос серверов, служит источником *последнего известного* установленного артефакта и результатов операций. Не выдавать это за подтверждение реального runtime-состояния.
- Автоматический rollback/recovery workflow, HA-awareness, параллельное исполнение независимых компонентов — вне MVP.

## Граница с DS-007
DS-006 задаёт правила формирования, проверки, хранения результатов и реакций оператора. DS-007 отвечает за Temporal Workflow/Activities, запуск/мониторинг Jenkins и Ansible, correlation, повторное подключение к внешним jobs, реальное исполнение шагов и техническое восстановление.

## Вопросы для детализации без фиктивного утверждения
- Точная физическая схема таблиц/API, технический формат plan snapshot, правила пересчёта при изменениях конфигурации.
- Нужны ли STOP/START при специализированных deploy jobs, которые управляют процессом сами; способ конфигурации такой семантики.
- Разграничение результатов операции, компонента и всего Execution, в т.ч. невозможность операционного завершения.
- Механизм durable distributed locks и точка их атомарного захвата.
- Production gate: SUCCEEDED означает завершённую раскатку *конкретного* Manifest; правила учёта ручных подтверждений должны быть проверяемыми.
