# DS-007 — Deployment Execution: принятые архитектурные решения (MVP)

**Дата:** 19.11.2026  
**Статус:** согласованные архитектурные решения по состоянию на 19.11.2026; техническая спецификация и реализация ещё не завершены.  
**Связь:** [DS-006 Deployment Planning](DS-006_Deployment_Planning_Overview_RU.md).

## Утверждённая модель исполнения

- **Component-based**: компоненты выполняются последовательно в порядке, допустимом с учётом зависимостей. Для каждого компонента выполняется его цепочка операций до перехода к следующему.
- Внутри одного компонента, размещённого на нескольких серверах целевого Environment, операция **STOP** запускается параллельно на всех требуемых серверах (**ALL_AT_ONCE**). Переход к **DEPLOY** разрешён только после подтверждённого завершения STOP на всех этих серверах; затем DEPLOY параллельно по серверам, общий барьер; затем START параллельно по серверам, общий барьер.
- Барьер означает проверку результатов **всех** соответствующих server-level шагов, а не просто успешную отправку внешних jobs.
- На ожидание результатов устанавливаются **таймауты**; бесконечного ожидания нет.
- При ошибке или таймауте выполнение **приостанавливается**, новые стадии не стартуют, оператор получает сообщение с контекстом (компонент, операция, серверы и результаты) и принимает решение.
- Минимальные действия оператора: **Retry step**, **Skip/Continue с явной фиксацией**, **Abort execution**. Решения и причины аудируются. Автоматического rollback в MVP нет.
- Не писать код на основании этих заметок без отдельного запроса.

## Иллюстрация

```text
Component A:
  STOP   server-1 || server-2 || server-3  -> barrier
  DEPLOY server-1 || server-2 || server-3  -> barrier
  START  server-1 || server-2 || server-3  -> barrier
Component B:
  STOP   ... -> barrier
  DEPLOY ... -> barrier
  START  ... -> barrier
```

## Согласование с DS-006 и ограничения

- STOP/START/VALIDATE могут быть отключены в DeploymentPlan согласно DS-006; схема выше показывает случай, когда STOP, DEPLOY и START включены.
- Порядок компонентов должен соблюдать правила dependency-aware planning DS-006; это решение не разрешает автоматически останавливать компоненты вне Release.
- При ошибке одного сервера уже запущенные параллельные jobs **не отменяются автоматически**: ждём их результатов до таймаута, затем показываем сводку оператору; новые стадии не стартуют.
- **Retry** запускается только для failed/timed-out targets после сверки с Jenkins/Ansible; уже выполняющиеся jobs не дублируются, подтверждённый поздний успех учитывается. Старый ответ не перезаписывает более новую попытку. Технический механизм correlation/idempotency, конкретные таймауты и критерии STOP/START ещё требуют детализации.
- **Skip/Continue решает оператор**: DS показывает предупреждения, требует явного подтверждения, комментария и аудита; не запрещает продолжение только из-за оценки риска. Пропущенный шаг — SKIPPED, не SUCCESS. После такого продолжения итог — COMPLETED_WITH_WARNINGS, который не засчитывается как успешный TESTING deployment для Production Gate.
- **Mark as Completed**: после исправления вне DS оператор может подтвердить выполненную операцию с обязательным комментарием; статус шага MANUALLY_COMPLETED, не автоматический SUCCESS. **Recovery**: после рестарта DS/Temporal Worker автоматически восстанавливает Workflow и сверяет внешние jobs; повторный запуск вслепую запрещён. Если достоверно определить состояние нельзя — пауза и решение оператора. Concurrency locks, реализация восстановления, статус при MANUALLY_COMPLETED и соответствующий Production Gate остаются открытыми.

## Уточнения от 19.11.2026

- После ошибки параллельной операции ждём уже запущенные jobs до таймаута и показываем сводку по всем серверам.
- Retry касается только failed/timed-out целей; перед повтором проверяется прежний внешний запуск. Если он ещё выполняется — не дублировать; если успешно завершён — учитывать результат.
- Запоздалый ответ предыдущей попытки не меняет состояние новой активной попытки.
- Temporal после сбоя Worker/DS продолжает управление при подтверждённом состоянии внешних jobs; неопределённость передаётся оператору.
- Operator Skip/Continue допускается после явного предупреждения и подтверждения с причиной. При Skip шаг сохраняет SKIPPED, итог после завершения — COMPLETED_WITH_WARNINGS, не удовлетворяет TESTING success Production Gate.
- Manual completion поддерживается отдельным статусом MANUALLY_COMPLETED и обязательным объяснением оператора; влияние на итоговый результат и Production Gate ещё не утверждено.
