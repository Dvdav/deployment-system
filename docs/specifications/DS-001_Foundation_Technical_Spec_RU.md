**Документ:** окончательное техническое задание для реализации, версия 1.1  
**Дата:** 19 ноября 2026 г.  
**Статус:** архитектурные решения согласованы; реализация не начата в рамках подготовки документа  
**Аудитория:** junior/middle разработчик, технический ревьюер и принимающий заказчик

## 1. Назначение и ожидаемый результат

DS — внутренняя корпоративная система для управления релизами и деплоями. Полный проект предполагает интеграции с Nexus 3, Jenkins и Ansible и позднее Temporal, ServiceNow и т.д. Этап DS-001 создаёт **техническую основу**, чтобы последующие небольшие функциональные этапы подключались к уже работающему приложению.

**Результат DS-001:** единый репозиторий с Java 21/Spring Boot backend, React/TypeScript/Vite frontend на Material UI, PostgreSQL + Flyway, двумя режимами запуска (Hybrid Development и Full Docker), системной страницей со статусом реального API/БД, воспроизводимыми тестами JUnit/Testcontainers/Vitest/Playwright и базовым Jenkins CI pipeline. Все проверки используют реальные экземпляры backend и PostgreSQL там, где это важно; никаких фиктивных данных о Nexus/компонентах/окружениях.

### 1.2 Границы и ограничения

- **В scope:** инженерная инфраструктура приложения, базовое системное API/страница, настоящие БД и тесты, документация, CI.
- **Вне scope:** Nexus connect/token encryption/Artifact Sources (DS-002/003), Component Registry, Environment Management и DnD, Jenkins/Ansible в качестве *управляемых DS контроллеров*, Temporal, Releases, Deployments, роли/SSO, промышленное развертывание, полноценные security gates.
- Jenkins в DS-001 — **только CI для сборки DS**, а не API-интеграция DS с Jenkins для деплоя.
- База данных **не должна** содержать заранее созданные таблицы из будущих бизнес-модулей.
- Ни один новый фреймворк или зависимость не добавляется без цели, проверки лицензии, оценки риска и отдельной записи в PR.
- Версии прямых зависимостей фиксируются; диапазоны и `latest` для production/build критичных зависимостей и образов не допускаются. Итоговые версии выбираются при реализации из актуального поддерживаемого набора и записываются в документацию; эта спецификация намеренно не выдумывает номера версий.

```text
│       │   │   └── system/                 # системная диагностика
│       │   └── resources/
│       │       ├── application.yml
│       │       └── db/migration/
│       │           └── V1__bootstrap.sql
│       └── test/java/<base-package>/
├── frontend/
│   ├── package.json
│   ├── package-lock.json              # committed; установка через npm ci
│   ├── index.html
│   ├── vite.config.ts
│   ├── tsconfig.json
│   ├── playwright.config.ts
│   ├── tests/e2e/
│   └── src/
│       ├── app/                       # App, routing, layout, MUI theme
│       ├── features/system/           # System Status
│       ├── shared/api/                # единый HTTP-клиент на fetch
│       └── main.tsx
├── docker/
│   ├── backend.Dockerfile
│   └── frontend.Dockerfile             # production-like serve статических файлов

```

**Уточнение:** `<base-package>` — единый выбранный Java package, зафиксировать при создании проекта (например, корпоративный namespace). Запрещены разные префиксы между модулями. Папки `nexus/`, `component/`, `environment/` добавляются **при реализации соответствующего функционала**, а не сейчас ради красивой структуры.

### 2.1 Архитектурные правила backend

1. Один Spring Boot executable и один Maven backend-module, пока нет доказанной потребности разбивать сборку.
2. Package-by-feature: `system` содержит HTTP/API и бизнес-логику диагностического функционала. Не создавать общие глобальные `controller`, `service`, `repository` для всех модулей.
3. Разделять контроллер и проверку БД, если это повышает тестируемость; не вводить по интерфейсу на каждый класс.
4. Доступ к PostgreSQL через Spring JDBC; JPA/Hibernate и H2 не подключать.
5. Configuration через Spring Boot environment/property binding; секреты не логировать.
6. REST API под префиксом `/api`; успешный ответ — JSON. Никаких внутренних исключений или SQL в публичном ответе.

### 2.2 Архитектурные правила frontend

1. `app/` — инициализация приложения, App Shell, MUI theme и маршрутизация.
2. `features/system/` — логика/компоненты System Status; будущие features автономны по структуре.
3. `shared/api/` — общий небольшой клиент на браузерном `fetch`, централизованная обработка сетевых ошибок. Axios не нужен.
4. MUI core — основные элементы интерфейса. Иные UI-пакеты и data-management библиотеки не добавлять без реального использования.
5. Переходы по URL должны работать после перезагрузки (SPA fallback при Full Docker).
6. В DS-001 нет sidebar, меню, навигационных заглушек и будущих разделов даже в disabled-виде. Добавлять их при реализации соответствующих этапов. Поддерживаются десктопные браузеры при ширине от 1280 px; мобильная адаптивность вне scope.

## 3. Интерфейсы и наблюдаемое поведение

### 3.1 Системное API

Отделить состояние процесса от готовности обслуживать запросы:

| Метод и маршрут | Значение | Поведение |
|---|---|---|
| `GET /api/health/live` | Liveness | `200` + JSON `{"status":"UP"}` когда backend отвечает; **не** обращается в БД |
| `GET /api/health/ready` | Readiness | Реальный короткий `SELECT 1` через JDBC; `200` + JSON `{"status":"UP","database":"UP"}` при доступной БД; `503` + `{"status":"DOWN","database":"DOWN"}` при недоступной |
| Неизвестный `/api/*` | Неизвестный API | HTTP 404; не отдавать HTML index вместо JSON для API-маршрутов |

Ненужные поля с внутренними адресами, стек-трейсами, паролями и SQL-сообщениями исключить. Для ошибочного API-ответа допустимо стандартное `status`, `error`/`message` без внутренних подробностей. Реализовать ровно два health endpoint, без alias `/api/health`, Spring Boot Actuator и Micrometer. Timeout readiness — 2 секунды по умолчанию, конфигурируемый через Spring configuration/environment. Ограничение учитывает и получение соединения из пула, и выполнение SQL; одного query timeout недостаточно. Документировать ограничения JDBC/пула. После восстановления БД readiness возвращается в UP без рестарта, если backend остался работоспособным. Статус на UI не кешировать.

**Нюанс:** если БД отсутствует уже во время запуска, Flyway/инициализация контекста может не позволить backend стартовать. Это допустимо, и frontend тогда должен показать `Backend unreachable`. Проверка `503` для БД выполняется при **потере БД после успешного запуска backend**, при условии что процесс продолжает отвечать HTTP.

### 3.2 System Status UI

Согласованный контракт из [Issue #4](https://github.com/Dvdav/deployment-system/issues/4):

#### 1. App Shell и маршрутизация
- Использовать уже настроенный в DS-001-01 React + TypeScript + Vite + MUI; не создавать второе приложение.
- Реализовать минимальный App Shell: верхняя панель с названием `Deployment System` и единственная основная область с состояниями сервисов. Не добавлять sidebar, меню или навигационные элементы; не дублировать заголовок `System Status` внутри страницы.
- Выбрать основной URL `/` либо `/system`, зафиксировать в README; прямая навигация и reload должны работать в доступном режиме. Full Docker SPA fallback будет завершён в DS-001-05.
- Не создавать в UI будущие разделы `Nexus`, `Components`, `Environments`, `Releases`, `Deployments` даже как disabled/`Not implemented` или заглушки. Добавлять их только в соответствующих последующих задачах.
- Соблюсти feature-based структуру: `src/app/`, `src/features/system/`, `src/shared/api/`.

#### 2. Реальный HTTP-клиент
- Реализовать небольшой wrapper над браузерным `fetch` (без Axios и тяжёлых state-management библиотек).
- Выполнять `GET /api/health/ready` по **относительному URL**, без hardcoded container hostnames, API/DB credentials или секретов.
- Настроить Vite dev proxy для `/api` к локальному backend в Hybrid Development; Full Docker reverse proxy входит в DS-001-05.
- Обрабатывать HTTP status и JSON contract: `200 {"status":"UP","database":"UP"}`, `503 {"status":"DOWN","database":"DOWN"}`.
- Различать сетевую ошибку, timeout, некорректный/unexpected response; не интерпретировать любую HTTP-ошибку как «PostgreSQL DOWN».
- Не кешировать результаты так, чтобы Refresh отображал старые данные.

#### 3. System Status UI и состояния
- Показывать два элемента состояния — **Backend API** и **PostgreSQL** — и кнопку `Refresh status`. Заголовок приложения `Deployment System` находится только в верхней панели; повторный заголовок `System Status` внутри страницы не нужен.
- При валидном `200 UP/UP`: `Backend UP`, `PostgreSQL UP`.
- При валидном `503 DOWN/DOWN` от readiness: backend **доступен как HTTP-сервис** (`Backend UP`), PostgreSQL `DOWN`; не путать readiness DOWN с недоступностью backend.
- При network failure, timeout или отсутствии ответа: `Backend UNREACHABLE`, `PostgreSQL UNKNOWN`.
- При неожиданном HTTP-коде, ошибке JSON или нарушении контракта: показывать диагностическую ошибку/`UNKNOWN`, **не придумывать** состояние PostgreSQL.
- При первом открытии страницы запускать проверку автоматически: до получения ответа значения/значки напротив обоих сервисов отсутствуют; индикатор `CircularProgress` из MUI и текст `Checking...` показываются в области кнопки проверки. Не показывать выдуманные промежуточные статусы.
- При ручном `Refresh status` показывать небольшой `CircularProgress` **внутри самой кнопки**, временно блокировать повторное нажатие. Во время повторной проверки разрешено оставить предыдущие значения, но только визуально приглушёнными и явно обозначенными как результаты прошлой проверки (не актуально подтверждённые). Отдельные спиннеры около Backend/PostgreSQL не нужны.
- По завершении проверки убирать spinner; напротив сервисов показывать зелёную галочку для `UP`, красный крестик для подтверждённого `DOWN`/недоступного backend, серый вопросительный знак или `UNKNOWN`, если состояние установить нельзя (например, PostgreSQL при недоступном backend). Не трактовать `503` от доступного backend как отказ самого backend. Вернуть кнопку в состояние `Refresh status`; индикатор не должен крутиться бесконечно при ошибке или timeout.
- Защититься от устаревших ответов и нескольких одновременных Refresh-запросов.
- Ошибки понятные человеку, но без stack traces, URL БД, credentials или внутренних подробностей.
- Поддерживать только десктопные браузеры при ширине окна **от 1280 px**; проверять читаемость статусов/ошибок/кнопки при такой ширине. Мобильную адаптивность и тестирование телефонных разрешений не выполнять.

## 4. PostgreSQL и миграции

1. PostgreSQL запускается из официального образа с закреплённой версией и SHA256 digest. Hybrid и Full Docker используют один явно именованный persistent volume, только последовательно. `down` сохраняет данные; поведение разрушительного reset зависит от объявления volume (external volume может не удаляться через `down -v`) и точно документируется.
2. Обязательные переменные: JDBC URL/host+port, DB name/user/password и runtime profile/port (конкретные имена переменных согласовать с настройкой Spring Boot и документировать).
3. Flyway запускается на backend старте. `V1__bootstrap.sql` обязательно создаёт единственную техническую таблицу `system_info` по схеме ниже. Пустая V1 не используется. Не создавать заранее бизнес-таблицы или фиктивные production-данные.
4. В тестах использовать тот же Flyway migration set, что и в приложении. Никакого `spring.jpa.hibernate.ddl-auto` и тестовой H2.
5. Для невалидной миграции backend startup завершается ошибкой (fail fast); состояние не маскируется зелёным статусом.
6. Проверить запись/чтение `system_info` через Spring JDBC и сохранение записи после рестарта с тем же volume. PostgreSQL Testcontainers-тест с реальными миграциями и изолированная проверка fail-fast обязательны уже в DS-001-02.

```sql
CREATE TABLE system_info (
    id INTEGER PRIMARY KEY,
    value VARCHAR(255) NOT NULL
);
```

Доступность Docker Engine, Compose, официальных images и Testcontainers на целевой машине пока не подтверждена. Проверить при реализации и зафиксировать результат или инфраструктурный блокер; не подменять PostgreSQL на H2.

## 5. Конфигурация, безопасность и зависимости

- `.env.example` содержит только имена переменных с безопасными примерами/плейсхолдерами, **не реальные секреты**. Реальный `.env` и локальные override-файлы игнорируются Git.
- JDBC пароль и любые будущие токены не включать в исходники, frontend bundle, HTTP responses и логи.
- Docker build не копирует `.env`, `.git`, локальные секреты и ненужные build артефакты; настроить `.dockerignore`.
- В Full Docker публиковать только порт frontend и только на `127.0.0.1`; backend и PostgreSQL доступны внутри Docker network. В Hybrid порт DB публикуется только на `127.0.0.1`.
- Приложение должно корректно запускаться без root внутри backend/frontend контейнеров, если использованные base images допускают это без чрезмерной сложности; сборочные и runtime images разделить multi-stage, где оправдано.
- Указать минимально необходимые версии Java, Maven, Node, npm, Docker/Compose, закрепить образ Java/Node/PostgreSQL/frontend-serving и соответствующие runtime dependencies. npm lockfile коммитится и используется `npm ci`, Maven dependency/plugin versions фиксируются.
- Никаких security gates, SAST/DAST/SBOM automation в качестве обязательного CI критерия DS-001. **Но** запрещено выдавать этот этап за production-security approved. Отдельная обязательная задача: security scanning + SBOM + license policy **до первого корпоративного развёртывания**; использовать корпоративные средства, чтобы не дублировать процессы.
- DS-001 не реализует OAuth/SSO/пользовательские роли. Демонстрация — локальная/изолированная, не выставлять приложение в публичную сеть.

## 6. Режимы запуска

Согласованные требования из [Issue #5](https://github.com/Dvdav/deployment-system/issues/5):

### 6.1 Два альтернативных режима
- **Hybrid:** `compose.dev.yaml` запускает только PostgreSQL; Spring Boot и React/Vite работают непосредственно на компьютере разработчика.
- **Full Docker:** `compose.yaml` поднимает PostgreSQL, Spring Boot и frontend одной командой `docker compose up --build -d`.
- Режимы **не поддерживают одновременную работу** с одной БД; README даёт безопасный порядок остановки одного режима и запуска другого.
- PostgreSQL в обоих режимах использует **один и тот же явно именованный persistent named volume**, а не случайно разные project-prefixed volumes. Имя/правила владения и переключения описать в README; никогда не подключать один PostgreSQL data directory к двум одновременно работающим экземплярам PostgreSQL.
- Использовать согласованные версии PostgreSQL и одинаковое назначение данных; в Hybrid DB может публиковаться исключительно на `127.0.0.1` для локального backend, в Full Docker порт DB на хост не публиковать.
- **Не писать дополнительных start/stop shell-скриптов**: только стандартные команды Compose и точная документация.

### 6.2 Dockerfiles и сборки
- `docker/backend.Dockerfile`: multi-stage build (Java 21 / Maven → конечный runtime с JAR + Java runtime); не тащить Maven и build-инструменты в runtime.
- `docker/frontend.Dockerfile`: multi-stage build (Node.js + Vite → только статические frontend assets в компактном web-server image, например Nginx); **не запускать Vite dev server в Full Docker**.
- По возможности запускать runtime контейнеры под непривилегированным пользователем; если у выбранного образа это невозможно без несоразмерной сложности, документировать причину.
- Использовать конкретные поддерживаемые версии базовых образов, **закреплённые по SHA256 digest**, без `latest`. Выбранные image refs/digests и процедура обновления должны быть воспроизводимыми и документированными; digest проверяется при реализации, не выдумывать.
- Frontend: `npm ci` и committed `package-lock.json`; backend: закреплённые Maven dependency/plugin versions. Не выполнять неявные обновления зависимостей во время сборки.
- Минимизировать зависимости; проверить необходимость runtime-утилит для healthchecks. `.dockerignore` исключает `.git`, `.env`, секреты, локальные build artefacts и `node_modules`; не передавать пароли через Docker build args и не встраивать их в frontend bundle.

### 6.3 Сеть и reverse proxy
- **Full Docker:** единственный опубликованный порт — порт frontend, привязанный **только к `127.0.0.1`** на машине разработчика. Backend и PostgreSQL не публиковать наружу.
- Frontend web server раздаёт статические файлы и проксирует относительные `/api/*` к backend по внутренней Docker-сети. Не хардкодить адреса контейнеров или секреты в JavaScript.
- SPA fallback для пользовательских UI путей: прямое открытие страницы и browser reload не дают 404; **не** превращать неизвестные `/api/*` в HTML frontend (`/api/*` остаётся API).
- **Hybrid:** Vite dev proxy направляет относительные `/api/*` на локальный backend. Определённые в README локальные порты согласованы с Spring Boot и не конфликтуют с Full Docker.

### 6.4 Постоянные данные и конфигурация
- PostgreSQL использует named volume; записи в `system_info` и Flyway history переживают `stop/start`, `down/up` и безопасное переключение Hybrid ↔ Full Docker.
- **Никогда автоматически не удалять volume при ошибках сборки, запуска или миграции.** `docker compose down` сохраняет данные, `docker compose down -v` может удалить подключённые volume и допускается только при намеренном сбросе. В README предупреждать особо, что при общем volume `down -v` опасен для данных обоих режимов.
- Конфигурация backend/DB через environment и локальный `.env`, создаваемый из `.env.example`. В Git хранить только пример с безопасными placeholders, **без настоящего DB password**; `.env` игнорировать в Git.
- Отличать адрес DB в Hybrid (`localhost`/loopback для backend на хосте) от Full Docker (имя сервиса внутри сети). Пользователь, база, пароль должны согласованно передаваться backend и PostgreSQL.
- Документировать особенность существующего volume: изменение пароля в `.env` **не меняет автоматически пароль уже инициализированного пользователя PostgreSQL**. Дать безопасную процедуру изменения пароля без потери данных и отдельную явно разрушительную процедуру сброса локальной БД.

### 6.5 Порядок запуска, healthchecks и восстановление
- PostgreSQL healthcheck через `pg_isready` каждые **5 секунд**; корректные параметры подключения и разумные timeout/retries/start period. `service_healthy` в `depends_on` удерживает запуск backend, пока PostgreSQL не готова принимать соединения.
- Spring Boot после старта выполняет Flyway; ошибочная миграция должна приводить к **неуспешному startup**, а не к ложному `healthy`.
- Backend healthcheck использует существующий `GET /api/health/ready` (DS-001-03), frontend healthcheck проверяет доступность его HTTP server (без лишних runtime-зависимостей). Все три контейнера отражают своё состояние в `docker compose ps`.
- Frontend **не обязан ожидать backend readiness** до начала обслуживания HTTP; если backend недоступен, сама страница открывается и показывает `Backend UNREACHABLE / PostgreSQL UNKNOWN` согласно DS-001-04.
- При потере PostgreSQL **после успешного запуска** backend, если процесс продолжает работать: `/api/health/live` остаётся `200 UP`, `/api/health/ready` возвращает `503 DOWN`, и UI показывает `Backend UP / PostgreSQL DOWN`; после восстановления БД readiness возвращается в `UP` без рестарта backend. Не путать backend container `unhealthy` (readiness DOWN) с завершившимся backend-процессом.
- Для локальных сервисов применить `restart: on-failure:3` (или корректный Compose-эквивалент) — **ограниченное восстановление после аварийного выхода**, без автоматического запуска остановленного локального стенда после перезагрузки компьютера; предусмотреть и описать проверку этого поведения на целевой версии Docker/Compose.
- `unhealthy` **сам по себе не инициирует автоматический restart**; не добавлять autoheal/watchdog/автоперезапуск по healthcheck в MVP. Не обещать, что `depends_on` поддерживает readiness-зависимость непрерывно после начального запуска.

### 6.6 Логи, ресурсы, отказы и очистка
- Логи backend через stdout/stderr, PostgreSQL/frontend — стандартные container logs. Просмотр через `docker compose ps` и `docker compose logs` (общие и по сервисам).
- Настроить ротацию логов: **10 MB на файл, максимум 3 файла на контейнер**, используя совместимый драйвер/настройку Docker. Не включать ELK/Loki и другие системы логирования.
- Не выводить в логи/HTTP ответы/образа пароли, токены, секреты, JDBC credentials и чувствительные детали.
- Нет жёстких лимитов CPU/RAM на этапе MVP. В README указать ориентировочные системные требования и команды контроля ресурсов (`docker stats`), а лимиты вводить позднее по измерениям.
- При ошибке сборки, Flyway или запуска показывать фактический failure и понятную диагностику; не выдавать частично запущенный стек за успешный. Данные volume не удалять.
- Остановка, удаление контейнеров/сетей и ручная очистка только ресурсов этого проекта — по инструкциям. **Никаких автоматических `docker system prune`, удаления чужих образов, volumes или агрессивных cleanup-скриптов.**

### 6.7 README — обязательная пошаговая инструкция
- Prerequisites: Docker Engine/Desktop + Compose, Java 21/Maven/Node/npm для Hybrid; требуемые версии, проверка инструментов, минимальные требования к машине и порты.
- Как создать `.env` из `.env.example`, придумать и установить **локальный тестовый пароль PostgreSQL**, задать имя DB/user, JDBC URL/host; безопасно проверить, что `.env` не попадёт в Git.
- **Пошаговый запуск Hybrid**, **пошаговый запуск Full Docker**, команды остановки и переключения **без потери состояния**, включая shared volume и запрет одновременного использования.
- Команды просмотра `ps`, healthchecks, логов, `docker stats`, диагностики недоступной БД, неработающего proxy, ошибочной Flyway migration, конфликтов портов и недоступных Docker-образов в корпоративной сети.
- Смена пароля существующей БД; обычная остановка vs **явно разрушительный** reset через `down -v` (учесть, что при явном external volume команда может не удалить его; привести точные команды, соответствующие реальному Compose).
- Указать, как подтвердить сохранение `system_info` после пересоздания контейнера и после переключения режимов. Ни один шаг запуска не должен зависеть от устных подсказок.

## 7. Автоматические тесты (обязательные)

### 7.1 Backend — JUnit + Spring Boot Test + Testcontainers

- Unit-тесты только для логики, в которой есть смысл тестировать правила; не создавать фиктивные тесты getter/setter.
- Интеграционный тест поднимает **реальную PostgreSQL Testcontainer**, применяет Flyway, вызывает readiness API и проверяет `200`, `UP`, `database=UP`.
- Отдельный тест моделирует **потерю БД после запуска** и проверяет `503`, `DOWN`, отсутствие stack trace в ответе. Для надёжности предусмотреть контролируемую остановку контейнера или эквивалентный независимый тест с реальным JDBC без замены бизнес API mock-результатом.
- `GET /api/health/live` продолжает возвращать `200`, если backend доступен при недоступной БД.
- Проверить `404` для неизвестного API пути; Flyway применяет только ожидаемые миграции.
- Тесты изолированы, повторяемы и не используют корпоративные сервисы.

### 7.2 Frontend — Vitest + React Testing Library

- Страница корректно показывает `UP` после успешного ответа.
- `DOWN` PostgreSQL и `UNREACHABLE` backend различаются; при отсутствии данных о БД показывается `UNKNOWN`.
- Первый запрос без выдуманных статусов, CircularProgress в области кнопки, блокировка повторного Refresh, завершение spinner при ошибке/timeout, защита от устаревших ответов; предыдущие значения при Refresh явно устаревшие.
- Валидный 503 readiness отображает Backend UP / PostgreSQL DOWN; некорректный JSON/HTTP не превращается в подтверждённый отказ БД. Десктопная ширина от 1280 px.
- В тестах frontend **допустимо** мокировать `fetch` для проверки состояний React; запрет на мок интеграций относится к демонстрации и E2E, а не к локальным unit-тестам.

### 7.3 E2E — Playwright

- Поднять полноценную тройку backend + PostgreSQL + frontend в изолированном тестовом окружении.
- Открыть реальный браузер, дождаться страницы и проверить статус API/БД (`UP`).
- Нажать `Refresh status`, проверить повторное отображение фактического статуса.
- Проверить отображение `Backend unreachable` при выключенном backend либо разрыве сетевого доступа; PostgreSQL не должен ошибочно показываться `DOWN` без данных от API.
- Не подменять backend API mocks в этом сквозном тесте.
- Подготовить browser dependencies/Playwright browsers в CI; окружение и версии браузеров закреплены средствами Playwright/lockfile.

**Тестовые команды:** для Maven `./mvnw test` либо `mvn test` согласно утверждённому bootstrap; для frontend `npm ci`, `npm run typecheck`, `npm run test`, `npm run build`, `npm run test:e2e`. Подготовить репозиторные scripts так, чтобы команды выполнялись без скрытых ручных шагов; если Playwright E2E запускается через Compose с отдельным файлом/профилем, указать точную команду.

## 8. Jenkins CI Pipeline

### 8.1 Триггеры и обязательные этапы

- Jenkins pipeline определяется `Jenkinsfile` в корне Monorepo.
- Trigger: каждый Pull Request / изменение ветки, которую сканирует корпоративная Jenkins multibranch конфигурация; детали вебхуков и credential Jenkins агента — задача инфраструктуры, README описывает предпосылки.
- Этапы:
  1. Checkout monorepo.
  2. Validate prerequisites (Java 21, Maven, Node/npm, Docker connectivity, доступный browser runner).
  3. Backend compile + JUnit + Spring Boot/Testcontainers tests.
  4. Frontend dependency install from lockfile + typecheck + Vitest + production build.
  5. Поднять реальный E2E stack и запустить Playwright.
  6. Опубликовать JUnit XML / тестовые результаты и Playwright traces/screenshots **при сбоях**, если поддерживается Jenkins.
  7. Cleanup test containers/Compose в `post { always { ... } }`, без удаления чужих ресурсов.
- **Любое падение сборки/тестов делает CI stage и итоговый build FAILED**, если не оформлено документированное временное исключение, согласованное владельцем проекта.
- Никаких блокирующих vulnerability/license/image scan gates на DS-001.

### 8.2 Требования к Jenkins agent

- Linux agent с Java 21, совместимыми Maven/Node, Docker Engine и Docker Compose plugin.
- Доступ к Docker daemon, достаточный для Testcontainers и E2E Compose. Доступ к Docker socket высокопривилегирован — агент должен быть выделенным/доверенным и подчиняться корпоративной политике. **Не** запускать привилегированные контейнеры или socket mounts в общем shared-agent без разрешения инфраструктуры.
- Доступность портов либо изолированные сети/динамические порты для параллельных job.
- Playwright browser dependencies доступны в закреплённом runner image либо установлены доверенным заранее утверждённым способом.
- Вывод CI не содержит секретов или runtime `.env` с паролями.
- Если такой агент пока недоступен, **не** считать Jenkins pipeline работающим и не принимать DS-001-07 без устранения блокера или документированного изменения требований.

- [ ] `/api/health/live` и `/api/health/ready` ведут себя согласно контракту.
- [ ] UI показывает реальный backend/DB status, включая ошибки и Refresh.
- [ ] Hybrid Development работает после выполнения README.
- [ ] Full Docker работает одной командой и корректно переживает повторный запуск.
- [ ] JUnit/Spring Boot Test + PostgreSQL Testcontainers выполняются и проверяют обработку отказов.
- [ ] Vitest + React Testing Library и Playwright E2E проходят на реальном стеке.
- [ ] Jenkins pipeline запускается на PR, публикует результаты, корректно блокирует на failed tests.
- [ ] Нет корпоративных API-заглушек, демонстрационных псевдоинтеграций или реальных секретов в репозитории.
- [ ] Документация объясняет запуск, сбои, порты, requirements, ограничения и приёмку.
- [ ] Каждая из семи задач имеет подтверждённую отдельную приёмку.

**Финальный приёмочный сценарий (исполнять на чистом окружении):**

1. Clone выбранного commit на машине с указанными prerequisites.
2. Создать локальный `.env` из `.env.example`, задать тестовый пароль БД.
3. Выполнить документированную Full Docker команду; дождаться healthy stack.
4. Открыть System Status и увидеть `Backend UP / PostgreSQL UP`.
5. Нажать Refresh и убедиться, что отображается новый реальный ответ.
6. После старта временно остановить PostgreSQL и проверить диагностический контракт: liveness backend остаётся UP, readiness — DOWN/503, если процесс продолжает работать; UI — `PostgreSQL DOWN`. При отказе backend UI показывает `Backend UNREACHABLE`, `PostgreSQL UNKNOWN`.
7. Восстановить БД и увидеть успешное возвращение к UP без ручного изменения кода.
8. Записать тестовое значение в `system_info`; проверить сохранность записи и Flyway history после `down/up` и переключения Full Docker → Hybrid → Full Docker. Проверить loopback-only порты, healthchecks, ограниченный restart и ротацию логов.
9. Пройти README Hybrid режим; убедиться в актуальном UI и API.
10. Запустить все backend/frontend/E2E тесты, увидеть SUCCESS в Jenkins на Pull Request.
11. Проверить `git status`/репозиторий/логи на отсутствие секретов, задокументировать известные ограничения и подписать итоговую приёмку.

## 11. Definition of Done

DS-001 **готов**, когда все семь задач приняты, финальный чек-лист пройден и подтверждён, функциональная демонстрация соответствует реальным ответам API/БД, Full Docker и Hybrid воспроизводимы, Jenkins build зелёный на фактическом PR, README актуален.

Не считать DS-001 готовым, если «зелёный» status нарисован на frontend, PostgreSQL подменяется H2, E2E заменён snapshot UI, Jenkinsfile не запускался на Jenkins agent, пароль закоммичен или объявлена готовность Nexus-интеграции без её реализации.

## 12. Риски и вопросы, не блокирующие подготовку ТЗ, но обязательные к проверке при реализации

| Вопрос | Ответственность | Когда закрыть |
|---|---|---|
| Конкретные поддерживаемые версии Spring Boot/MUI/PostgreSQL/Node/Playwright и base images | Разработчик + reviewer, с проверкой корпоративных ограничений | DS-001-01 / DS-001-05 |
| Java base-package, HTTP-порты, выбор route `/` или `/system` | Разработчик фиксирует в README/PR | DS-001-01 / DS-001-04 |
| Jenkins agent с доверенным Docker-доступом/Testcontainers/Playwright | Инфраструктура + разработчик | До приёмки DS-001-07 |
| Стратегия параллельных E2E Jenkins builds (порты, workspace, cleanup) | Разработчик/CI owner | DS-001-07 |
| Репозиторий npm/Maven и доступность скачивания зависимостей в корпоративной сети | Инфраструктура + разработчик | DS-001-01 |
| Ключевой вопрос будущего Component UI: name == artifactId либо свободно редактируемое artifactId | Заказчик + архитектор | DS-004 (не относится к DS-001) |
| Реализация encrypted-token storage и key rotation | Заказчик + разработчик | DS-002 |
| Security scans, SBOM, licenses и release gates | Инфобез/CI owner | **До корпоративного развёртывания**, не в DS-001 |

## 13. План следующих этапов (не обязательства DS-001)

- **DS-002:** Nexus 3 подключения (несколько серверов), ввод токена оператором и шифрование при сохранении, `Check Connection` (без авто-загрузки огромного перечня repositories).
- **DS-003:** ручная регистрация и проверка Maven repositories как `ArtifactSource` с выбранным оператором типом RELEASE/SNAPSHOT, поиск реальных Maven артефактов.
- **DS-004:** Component Registry, связи с Artifact Sources и просмотр версий без выбора release версии.
- **DS-005:** Environment Management — группы DEVELOPMENT/TESTING/PRODUCTION, Drag & Drop перестановка и перенос между группами с подтверждением, ручное добавление серверов, компонентные labels через реальный Registry.
- **DS-006:** Jenkins/Ansible controller/job/parameter integration.
- **DS-007:** Release Management + immutable Manifest.
- **DS-008:** реальное DEV/UAT Deployment Planning & Execution.

**Отдельный контроль:** NEXT stage DS-002 можно начинать только после приёмки DS-001. Исключения/параллельные подготовительные работы не должны подменять критерии завершения DS-001.
