**Проект:** Deployment System (DS) / Release Management Platform  
**Документ:** окончательное техническое задание для реализации, версия 1.0  
**Дата:** 16 ноября 2026 г.  
**Статус:** архитектурные решения согласованы; реализация не начата в рамках подготовки документа  
**Аудитория:** junior/middle разработчик, технический ревьюер и принимающий заказчик  
**Принцип поставки:** семь последовательно принимаемых задач + финальная сквозная приёмка.

## 1. Назначение и ожидаемый результат

DS — внутренняя корпоративная система для управления релизами и деплоями. Полный проект предполагает интеграции с Nexus 3, Jenkins и Ansible и позднее Temporal, ServiceNow и т.д. Этап DS-001 создаёт **техническую основу**, чтобы последующие небольшие функциональные этапы подключались к уже работающему приложению.

**Результат DS-001:** единый репозиторий с Java 21/Spring Boot backend, React/TypeScript/Vite frontend на Material UI, PostgreSQL + Flyway, двумя режимами запуска (Hybrid Development и Full Docker), системной страницей со статусом реального API/БД, воспроизводимыми тестами JUnit/Testcontainers/Vitest/Playwright и базовым Jenkins CI pipeline. Все проверки используют реальные экземпляры backend и PostgreSQL там, где это важно; никаких фиктивных данных о Nexus/компонентах/окружениях.

### 1.2 Границы и ограничения

- **В scope:** инженерная инфраструктура приложения, базовое системное API/страница, настоящие БД и тесты, документация, CI.
- **Вне scope:** Nexus connect/token encryption/Artifact Sources (DS-002/003), Component Registry, Environment Management и DnD, Jenkins/Ansible в качестве *управляемых DS контроллеров*, Temporal, Releases, Deployments, роли/SSO, промышленное развертывание, полноценные security gates.
- Jenkins в DS-001 — **только CI для сборки DS**, а не API-интеграция DS с Jenkins для деплоя.
- База данных **не должна** содержать заранее созданные таблицы из будущих бизнес-модулей.

- Версии прямых зависимостей фиксируются; диапазоны и `latest` для production/build критичных зависимостей и образов не допускаются. Итоговые версии выбираются при реализации из актуального поддерживаемого набора и записываются в документацию; эта спецификация намеренно не выдумывает номера версий.

## 2. Конечная структура репозитория

```text
deployment-system/
├── backend/
│   ├── pom.xml
│   └── src/
│       ├── main/
│       │   ├── java/<base-package>/
│       │   │   ├── DeploymentSystemApplication.java
│       │   │   └── system/                 # системная диагностика
│       │   └── resources/
│       │       ├── application.yml
│       │       └── db/migration/
│       │           └── V1__bootstrap.sql
│       └── test/java/<base-package>/
├── frontend/
│   ├── package.json
│   ├── package-lock.json              # либо иной один согласованный lockfile
│   ├── index.html
│   ├── vite.config.ts
│   ├── tsconfig.json
│   ├── playwright.config.ts
│   ├── tests/e2e/
│   └── src/
│       ├── app/                       # App, routing, layout, MUI theme
│       ├── features/system/           # System Status
│       ├── shared/api/                # единый HTTP-клиент на fetch
│       └── main.tsx
├── docker/
│   ├── backend.Dockerfile
│   └── frontend.Dockerfile             # production-like serve статических файлов
├── compose.yaml                       # полный запуск
├── compose.dev.yaml                   # только dev-инфраструктура (БД)
├── .env.example
├── .gitignore
├── .dockerignore                      # в нужных build contexts
├── Jenkinsfile
└── README.md
```

**Уточнение:** `<base-package>` — единый выбранный Java package, зафиксировать при создании проекта (например, корпоративный namespace). Запрещены разные префиксы между модулями. Папки `nexus/`, `component/`, `environment/` добавляются **при реализации соответствующего функционала**, а не сейчас ради красивой структуры.

### 2.1 Архитектурные правила backend

1. Один Spring Boot executable и один Maven backend-module, пока нет доказанной потребности разбивать сборку.
2. Package-by-feature: `system` содержит HTTP/API и бизнес-логику диагностического функционала. Не создавать общие глобальные `controller`, `service`, `repository` для всех модулей.
3. Разделять контроллер и проверку БД, если это повышает тестируемость; не вводить по интерфейсу на каждый класс.
4. Доступ к PostgreSQL через Spring JDBC; JPA/Hibernate и H2 не подключать.
5. Configuration через Spring Boot environment/property binding; секреты не логировать.
6. REST API под префиксом `/api`; успешный ответ — JSON. Никаких внутренних исключений или SQL в публичном ответе.

### 2.2 Архитектурные правила frontend

1. `app/` — инициализация приложения, App Shell, MUI theme и маршрутизация.
2. `features/system/` — логика/компоненты System Status; будущие features автономны по структуре.
3. `shared/api/` — общий небольшой клиент на браузерном `fetch`, централизованная обработка сетевых ошибок. Axios не нужен.
4. MUI core — основные элементы интерфейса. Иные UI-пакеты и data-management библиотеки не добавлять без реального использования.
5. Переходы по URL должны работать после перезагрузки (SPA fallback при Full Docker).
6. Неподготовленные разделы не должны выглядеть работающими; допускается неактивная навигация `Nexus`, `Components`, `Environments`, `Releases`, `Deployments` с понятной пометкой «Not implemented» или скрытие до реализации. Запрещены фальшивые статусы и моковые бизнес-данные.

## 3. Интерфейсы и наблюдаемое поведение

### 3.1 Системное API

Отделить состояние процесса от готовности обслуживать запросы:

| Метод и маршрут | Значение | Поведение |
|---|---|---|
| `GET /api/health/live` | Liveness | `200` + JSON `{"status":"UP"}` когда backend отвечает; **не** обращается в БД |
| `GET /api/health/ready` | Readiness | Реальный короткий `SELECT 1` через JDBC; `200` + JSON `{"status":"UP","database":"UP"}` при доступной БД; `503` + `{"status":"DOWN","database":"DOWN"}` при недоступной |
| `GET /api/health` | Совместимый UI health endpoint | Эквивалент readiness для удобства страницы; тот же status mapping |
| Неизвестный `/api/*` | Неизвестный API | HTTP 404; не отдавать HTML index вместо JSON для API-маршрутов |

Ненужные поля с внутренними адресами, стек-трейсами, паролями и SQL-сообщениями исключить. Для ошибочного API-ответа допустимо стандартное `status`, `error`/`message` без внутренних подробностей. Параметры health-check: умеренный timeout запроса к БД, предсказуемый HTTP-код, отсутствие кеширования статуса на UI.

**Нюанс:** если БД отсутствует уже во время запуска, Flyway/инициализация контекста может не позволить backend стартовать. Это допустимо, и frontend тогда должен показать `Backend unreachable`. Проверка `503` для БД выполняется при **потере БД после успешного запуска backend**, при условии что процесс продолжает отвечать HTTP.

### 3.2 System Status UI

Публичная стартовая страница `/` либо `/system` (выбрать один основной путь и задокументировать) показывает:

- Название `Deployment System` и раздел `System Status`.
- Backend API: `UP` при успешном ответе API, `UNREACHABLE` при сетевой ошибке, ожидании/timeout или невозможности соединения.
- PostgreSQL: `UP`/`DOWN` на основании ответа readiness; `UNKNOWN` при недоступном backend — не утверждать, будто БД точно не работает.
- Кнопка `Refresh status` для повторного запроса; индикатор загрузки и понятная ошибка.
- Все значения берутся из реального backend, а не из frontend-констант.
- Меню готово к дальнейшему расширению; на узком экране информация остаётся читаемой.

**Контракт взаимодействия:** браузер запрашивает `/api/health` через одинаковый относительный путь в обоих режимах. В Hybrid настроить Vite dev proxy на локальный backend; в Full Docker — reverse proxy для `/api` через сервис, отдающий frontend. Не зашивать в собранный JavaScript внутренние hostname контейнеров и DB credentials.

## 4. PostgreSQL и миграции

1. PostgreSQL запускается из закреплённого официального образа, с persistent named volume в Full Docker; при `docker compose down` данные сохраняются, при `down -v` удаляются — это явно документировать.
2. Обязательные переменные: JDBC URL/host+port, DB name/user/password и runtime profile/port (конкретные имена переменных согласовать с настройкой Spring Boot и документировать).
3. Flyway запускается на backend старте. **Первая миграция** `V1__bootstrap.sql` создаёт минимальный технический объект лишь при реальной потребности; допустима валидная «пустая» baseline-миграция. Не создавать заранее `nexus`, `component`, `release` и прочие бизнес-таблицы.
4. В тестах использовать тот же Flyway migration set, что и в приложении. Никакого `spring.jpa.hibernate.ddl-auto` и тестовой H2.
5. Для невалидной миграции backend startup завершается ошибкой (fail fast); состояние не маскируется зелёным статусом.
6. Для теста сохранности volume использовать хотя бы одну небольшую тестовую запись в **временную проверочную таблицу, создаваемую вручную исключительно в тестовой среде**, либо явно наблюдаемый persisted state БД; не добавлять проверочные бизнес-таблицы в production миграции.

## 5. Конфигурация, безопасность и зависимости

- `.env.example` содержит только имена переменных с безопасными примерами/плейсхолдерами, **не реальные секреты**. Реальный `.env` и локальные override-файлы игнорируются Git.
- JDBC пароль и любые будущие токены не включать в исходники, frontend bundle, HTTP responses и логи.
- Docker build не копирует `.env`, `.git`, локальные секреты и ненужные build артефакты; настроить `.dockerignore`.
- Для Full Docker DB не публиковать наружу по умолчанию; backend доступен только frontend в Docker network, если для нужного UX нет отдельного обоснования. Для Hybrid можно явно открыть DB только на loopback `127.0.0.1`, чтобы подключить локальный backend.
- Приложение должно корректно запускаться без root внутри backend/frontend контейнеров, если использованные base images допускают это без чрезмерной сложности; сборочные и runtime images разделить multi-stage, где оправдано.
- Указать минимально необходимые версии Java, Maven, Node, npm, Docker/Compose, закрепить образ Java/Node/PostgreSQL/frontend-serving и соответствующие runtime dependencies. npm lockfile коммитится и используется `npm ci`, Maven dependency/plugin versions фиксируются.
- Никаких security gates, SAST/DAST/SBOM automation в качестве обязательного CI критерия DS-001. **Но** запрещено выдавать этот этап за production-security approved. Отдельная обязательная задача: security scanning + SBOM + license policy **до первого корпоративного развёртывания**; использовать корпоративные средства, чтобы не дублировать процессы.
- DS-001 не реализует OAuth/SSO/пользовательские роли. Демонстрация — локальная/изолированная, не выставлять приложение в публичную сеть.

## 6. Режимы запуска

### 6.1 Hybrid Development

1. Поднять PostgreSQL командой уровня `docker compose -f compose.dev.yaml up -d`.
2. Запустить backend локально через Maven, передав соответствующий конфигурационный профиль и локальные переменные.
3. Запустить frontend локально через npm/Vite; Vite proxy направляет `/api` на локальный Spring Boot.
4. Открыть адрес Vite; проверить реальный status + refresh.
5. Изменение React кода подхватывается через HMR; Java дебаггер подключается к локальному JVM-процессу.
6. README документирует точные команды, default порты, Docker/Java/Node prerequisites, startup order и решения типичных ошибок (занятый порт, недоступная БД, миграция, CORS/proxy).

### 6.2 Full Docker

1. Выполнить `docker compose up --build -d` из корня репозитория.
2. Compose поднимает PostgreSQL, backend и frontend (после готовности зависимостей; для PostgreSQL использовать healthcheck, а не простой порядок запуска).
3. Frontend доступен на документированном адресе хоста, API — по `/api` через reverse proxy frontend.
4. Проверить страницу, health, перезапуск и сохранение PostgreSQL volume.
5. Выполнить `docker compose down`; данные не удаляются без опции `-v`.
6. Ошибки запуска видимы в `docker compose ps/logs`; startup не должен бесконечно выдавать ложный success.

## 7. Автоматические тесты (обязательные)

### 7.1 Backend — JUnit + Spring Boot Test + Testcontainers

- Unit-тесты только для логики, в которой есть смысл тестировать правила; не создавать фиктивные тесты getter/setter.
- Интеграционный тест поднимает **реальную PostgreSQL Testcontainer**, применяет Flyway, вызывает readiness API и проверяет `200`, `UP`, `database=UP`.
- Отдельный тест моделирует **потерю БД после запуска** и проверяет `503`, `DOWN`, отсутствие stack trace в ответе. Для надёжности предусмотреть контролируемую остановку контейнера или эквивалентный независимый тест с реальным JDBC без замены бизнес API mock-результатом.
- `GET /api/health/live` продолжает возвращать `200`, если backend доступен при недоступной БД.
- Проверить `404` для неизвестного API пути; Flyway применяет только ожидаемые миграции.
- Тесты изолированы, повторяемы и не используют корпоративные сервисы.

### 7.2 Frontend — Vitest + React Testing Library

- Страница корректно показывает `UP` после успешного ответа.
- `DOWN` PostgreSQL и `UNREACHABLE` backend различаются; при отсутствии данных о БД показывается `UNKNOWN`.
- Состояние loading и кнопка обновления; повторный запрос действительно обновляет отображение.
- В тестах frontend **допустимо** мокировать `fetch` для проверки состояний React; запрет на мок интеграций относится к демонстрации и E2E, а не к локальным unit-тестам.

### 7.3 E2E — Playwright

- Поднять полноценную тройку backend + PostgreSQL + frontend в изолированном тестовом окружении.
- Открыть реальный браузер, дождаться страницы и проверить статус API/БД (`UP`).
- Нажать `Refresh status`, проверить повторное отображение фактического статуса.
- Проверить отображение `Backend unreachable` при выключенном backend либо разрыве сетевого доступа; PostgreSQL не должен ошибочно показываться `DOWN` без данных от API.
- Не подменять backend API mocks в этом сквозном тесте.
- Подготовить browser dependencies/Playwright browsers в CI; окружение и версии браузеров закреплены средствами Playwright/lockfile.

**Тестовые команды:** для Maven `./mvnw test` либо `mvn test` согласно утверждённому bootstrap; для frontend `npm ci`, `npm run typecheck`, `npm run test`, `npm run build`, `npm run test:e2e`. Подготовить репозиторные scripts так, чтобы команды выполнялись без скрытых ручных шагов; если Playwright E2E запускается через Compose с отдельным файлом/профилем, указать точную команду.

## 8. Jenkins CI Pipeline

### 8.1 Триггеры и обязательные этапы

- Jenkins pipeline определяется `Jenkinsfile` в корне Monorepo.
- Trigger: каждый Pull Request / изменение ветки, которую сканирует корпоративная Jenkins multibranch конфигурация; детали вебхуков и credential Jenkins агента — задача инфраструктуры, README описывает предпосылки.
- Этапы:
  1. Checkout monorepo.
  2. Validate prerequisites (Java 21, Maven, Node/npm, Docker connectivity, доступный browser runner).
  3. Backend compile + JUnit + Spring Boot/Testcontainers tests.
  4. Frontend dependency install from lockfile + typecheck + Vitest + production build.
  5. Поднять реальный E2E stack и запустить Playwright.
  6. Опубликовать JUnit XML / тестовые результаты и Playwright traces/screenshots **при сбоях**, если поддерживается Jenkins.
  7. Cleanup test containers/Compose в `post { always { ... } }`, без удаления чужих ресурсов.
- **Любое падение сборки/тестов делает CI stage и итоговый build FAILED**, если не оформлено документированное временное исключение, согласованное владельцем проекта.
- Никаких блокирующих vulnerability/license/image scan gates на DS-001.

### 8.2 Требования к Jenkins agent

- Linux agent с Java 21, совместимыми Maven/Node, Docker Engine и Docker Compose plugin.
- Доступ к Docker daemon, достаточный для Testcontainers и E2E Compose. Доступ к Docker socket высокопривилегирован — агент должен быть выделенным/доверенным и подчиняться корпоративной политике. **Не** запускать привилегированные контейнеры или socket mounts в общем shared-agent без разрешения инфраструктуры.
- Доступность портов либо изолированные сети/динамические порты для параллельных job.
- Playwright browser dependencies доступны в закреплённом runner image либо установлены доверенным заранее утверждённым способом.
- Вывод CI не содержит секретов или runtime `.env` с паролями.
- Если такой агент пока недоступен, **не** считать Jenkins pipeline работающим и не принимать DS-001-07 без устранения блокера или документированного изменения требований.

## 9. Последовательность реализации: задачи DS-001-01 … DS-001-07

Каждая задача выполняется отдельным PR или отчётливо выделенной последовательностью коммитов. **Нельзя начинать следующую задачу как принятую, пока заказчик не увидит проверку предыдущей.** Разрешена техническая подготовка параллельно, но завершение этапа фиксируется отдельно.

### DS-001-01 — Monorepo и bootstrap

**Цель:** создать единую структуру и минимальные сборочные проекты.

**Пошагово:**
1. Создать Git monorepo с папками `backend/`, `frontend/`, `docker/`, README, `.gitignore`, `.env.example`.
2. Настроить backend Maven Java 21 с Spring Boot starter web + JDBC + Flyway + PostgreSQL driver и тестовыми зависимостями по необходимости. Не подключать ORM.
3. Настроить frontend React + TypeScript + Vite + MUI + минимальный router, если действительно нужен для маршрутов. Подключить lockfile.
4. Создать bootstrap backend и страницу React с заголовком `Deployment System`; никаких симулированных статусов.
5. Настроить команды backend и frontend сборки; в README указать prerequisites.

**Проверка:** чистый `mvn`/`./mvnw` compile и `npm ci && npm run build` проходят на машине разработчика; исходники не содержат секретов; структура соответствует утверждённой.

**Не входит:** реальный health endpoint, Flyway persistence, Docker/CI.

**Артефакты приёмки:** ссылка на PR/commit, вывод сборки, краткое объяснение дерева проекта.

### DS-001-02 — PostgreSQL + Flyway

**Цель:** рабочая локальная БД и управляемые миграции.

**Пошагово:**
1. Добавить PostgreSQL в `compose.dev.yaml` с persistent volume; опционально `127.0.0.1` binding для Hybrid.
2. Настроить Spring JDBC properties только через env/config variables.
3. Подключить Flyway auto-migrate и создать первую baseline/bootstrapping миграцию.
4. Проверить работу с пустым volume и с уже заполненной Flyway history.
5. Явно отобразить ошибки конфигурации и failed migration в логах без паролей.
6. Задокументировать процедуру сброса исключительно локальной БД.

**Проверка:** Flyway schema history создана; две последовательные загрузки не приводят к повторному выполнению миграции; при испорченной миграции приложение не сообщает readiness UP. Существование бизнес-таблиц не требуется.

**Артефакты:** вывод Flyway/SQL inspection без секретов, команды запуска и остановки DB.

### DS-001-03 — Backend health API

**Цель:** реальное диагностическое API.

**Пошагово:**

**Проверка:** curl на все три endpoint, разрыв БД после старта, коды/тело ответов соответствуют разделу 3.1. Если backend стартовать нельзя без БД, зафиксировать это отдельно как ожидаемое fail-fast поведение.

**Артефакты:** HTTP response examples и тестовый чек-лист.

## 10. Единый протокол приёмки каждой задачи

Для каждого DS-001-XX разработчик обязан предоставить:

1. Ссылку на PR/commit с номером задачи, кратким описанием и списком затронутых файлов.
2. **Что реализовано** и что сознательно не реализовано; никаких обещаний выдать неполное за готовое.
3. Точные команды запуска/проверки с ожидаемыми результатами.
4. Тесты/скриншоты/логи проверки и список известных ограничений.
5. Краткую демонстрацию заказчику — по месту этапа, без фальшивых данных.
6. Отметку `Accepted` **только после подтверждения заказчиком**; найденные дефекты исправляются в рамках текущей задачи.

Разработчик не обязан строить UI для этапа БД, если нет полезного пользовательского сценария; его приёмка проводится воспроизводимыми командами/тестами. Для DS-001-04 и выше приёмка включает браузер.

### 10.1 Итоговый checklist DS-001

- [ ] Monorepo структура и зафиксированные зависимости, backend и frontend компилируются.
- [ ] PostgreSQL поднимается из Compose, Flyway применяет миграции.
- [ ] `/api/health/live` и `/api/health/ready` ведут себя согласно контракту.
- [ ] UI показывает реальный backend/DB status, включая ошибки и Refresh.
- [ ] Hybrid Development работает после выполнения README.
- [ ] Full Docker работает одной командой и корректно переживает повторный запуск.
- [ ] JUnit/Spring Boot Test + PostgreSQL Testcontainers выполняются и проверяют обработку отказов.
- [ ] Vitest + React Testing Library и Playwright E2E проходят на реальном стеке.
- [ ] Jenkins pipeline запускается на PR, публикует результаты, корректно блокирует на failed tests.
- [ ] Нет корпоративных API-заглушек, демонстрационных псевдоинтеграций или реальных секретов в репозитории.
- [ ] Документация объясняет запуск, сбои, порты, requirements, ограничения и приёмку.
- [ ] Каждая из семи задач имеет подтверждённую отдельную приёмку.

**Финальный приёмочный сценарий (исполнять на чистом окружении):**

1. Clone выбранного commit на машине с указанными prerequisites.
2. Создать локальный `.env` из `.env.example`, задать тестовый пароль БД.
3. Выполнить документированную Full Docker команду; дождаться healthy stack.
4. Открыть System Status и увидеть `Backend UP / PostgreSQL UP`.
5. Нажать Refresh и убедиться, что отображается новый реальный ответ.
6. После старта временно остановить PostgreSQL и проверить диагностический контракт: liveness backend остаётся UP, readiness — DOWN/503, если процесс продолжает работать; UI — `PostgreSQL DOWN`. При отказе backend UI показывает `Backend UNREACHABLE`, `PostgreSQL UNKNOWN`.
7. Восстановить БД и увидеть успешное возвращение к UP без ручного изменения кода.
8. Перезапустить Docker Compose и убедиться, что persistent volume сохранился.
9. Пройти README Hybrid режим; убедиться в актуальном UI и API.
10. Запустить все backend/frontend/E2E тесты, увидеть SUCCESS в Jenkins на Pull Request.
11. Проверить `git status`/репозиторий/логи на отсутствие секретов, задокументировать известные ограничения и подписать итоговую приёмку.

## 11. Definition of Done

DS-001 **готов**, когда все семь задач приняты, финальный чек-лист пройден и подтверждён, функциональная демонстрация соответствует реальным ответам API/БД, Full Docker и Hybrid воспроизводимы, Jenkins build зелёный на фактическом PR, README актуален.

Не считать DS-001 готовым, если «зелёный» status нарисован на frontend, PostgreSQL подменяется H2, E2E заменён snapshot UI, Jenkinsfile не запускался на Jenkins agent, пароль закоммичен или объявлена готовность Nexus-интеграции без её реализации.

## 12. Риски и вопросы, не блокирующие подготовку ТЗ, но обязательные к проверке при реализации
